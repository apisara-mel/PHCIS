# งานการเงิน (Finance / Payment) — Use Cases & Edge Cases

Reference doc for `src/pages/finance/FinancePaymentPage.jsx` and its 13 sections.
Written against the mock/prototype implementation (`src/data/financePaymentPrototype.js`
+ `src/data/financeReportsPrototype.js`, session-local `queue` state — nothing persists
past a page reload). Use this for QA, manual test scripts, or as the basis for real
backend acceptance criteria once this module gets wired to real data.

Each section: **Use cases** (happy-path + valid variations) then **Edge cases**
(boundary conditions, invalid input, empty states, concurrency).

> **§14 Defect log** เก็บบั๊ก 4 ตัวที่เจอตอนตรวจ TOR รอบ 2026-07-31 — แก้และยืนยันครบแล้ว
> ใช้เป็น regression script ได้เลย

### Use cases

| # | Actor | Scenario | Expected result |
|---|---|---|---|
| UC-1.1 | แคชเชียร์ | เปิดหน้า `/finance`, ดูคิวทั้งหมด | เห็นตาราง 8 รายการ, การ์ดสรุป 4 ใบ (รอชำระ/ชำระแล้ว/ค้างชำระ/ยกเลิก) ตรงกับข้อมูล |
| UC-1.2 | แคชเชียร์ | กดแท็บสถานะ "รอชำระเงิน" | ตารางกรองเหลือเฉพาะแถว status=pending |
| UC-1.3 | แคชเชียร์ | ค้นหาด้วยชื่อ/HN/คิว ในกล่องค้นหา | ตารางกรองแบบ real-time; มี suggestion dropdown พร้อม badge คิว+HN |
| UC-1.4 | แคชเชียร์ | คลิกแถว หรือปุ่ม "ชำระเงิน" ของแถวสถานะ pending | เปิด modal บันทึกรับเงิน แสดงรายการแยกหมวดหมู่ (ตรวจรักษา/lab/รังสี/ยา/เวชภัณฑ์/อื่นๆ) |
| UC-1.5 | แคชเชียร์ | เลือกวิธีชำระเงิน + กรอกจำนวนเงินที่รับ ≥ ยอดที่ต้องชำระ + กรอกชื่อผู้ชำระ | ระบบคำนวณเงินทอนอัตโนมัติ, ปุ่ม "บันทึกและพิมพ์ใบเสร็จ" เปิดใช้งาน |
| UC-1.6 | แคชเชียร์ | กด "บันทึกและพิมพ์ใบเสร็จ" | สถานะแถวเปลี่ยนเป็น "ชำระแล้ว", ออกเลขที่ใบเสร็จใหม่ (`RE69-####`), การ์ดสรุป/แท็บนับใหม่ทันที, modal ปิด |
| UC-1.7 | แคชเชียร์ | เปิดใบเสร็จที่ชำระแล้ว/ยกเลิกแล้ว | modal เป็น read-only, ปุ่มเปลี่ยนเป็น "พิมพ์ใบเสร็จ" (เรียก `window.print()`) |
| UC-1.8 | แคชเชียร์ | เปิดใบเสร็จ "ชำระแล้ว" แล้วกด "ยกเลิกใบเสร็จ" | เปิดฟอร์มยกเลิก (เหตุผลจากลิสต์ + รายละเอียด + ผู้อนุมัติ + ตำแหน่ง + วันที่อัตโนมัติ) |
| UC-1.9 | แคชเชียร์ | ยืนยันการยกเลิก | สถานะเป็น "ยกเลิกใบเสร็จ", บันทึกเหตุผล/ผู้อนุมัติ/ตำแหน่ง/วันที่ไว้ในใบเสร็จ, แสดงปุ่ม "ยกเลิกใบเสร็จ" หายไป (โหลดใหม่จะเห็น record เดิม) |
| UC-1.10 | แคชเชียร์ | เลือกประเภทส่วนลด "ยกเว้น" หรือ "ลดหย่อน" + ประเภทย่อย + %/จำนวนเงิน | ยอดที่ต้องชำระคำนวณใหม่ตามส่วนลดทันที |

### Edge cases

- ยอดที่ต้องชำระ = ฿0 (สิทธิ coverage 100%, F002) — ปุ่มบันทึกต้องยังกดได้แม้ "จำนวนเงินที่รับ" = 0 (0 ≥ 0)
- กรอกจำนวนเงินที่รับ **น้อยกว่า** ยอดที่ต้องชำระ → ปุ่มบันทึกต้อง disabled (validation: `Number(received) < netDue`)
- ไม่กรอก "ได้รับเงินจาก" (ลบ default ออกจนว่าง) → ปุ่มบันทึก disabled
- ยกเลิกการเลือกรายการทั้งหมด (`selected.size === 0`) → ปุ่มบันทึกต้อง disabled
- **เลือกบางรายการ (partial selection)** → ยอดรวม/สิทธิ/ยอดที่ต้องชำระ ต้องคิดใหม่จากเฉพาะรายการที่ติ๊ก
  — **ปัจจุบันไม่เป็นเช่นนั้น ดู [DEF-3](#def-3--ติ๊กเลือกรายการไม่มีผลกับยอดเงิน-)**
- ติ๊กออกจนเหลือรายการที่ `covered = amount` (สิทธิจ่ายเต็ม) รายการเดียว → ยอดที่ต้องชำระควรเป็น ฿0
  และปุ่มบันทึกยังต้องกดได้
- รายการที่ `selfPayOnly: true` (นอกสิทธิ เช่น F004) ต้องมี `covered = 0` เสมอ ไม่ว่าสิทธิของ visit
  จะ coverage เท่าไหร่ — ทดสอบว่าไม่มีสิทธิใดมาหักลดรายการนอกสิทธิได้
- ใส่ส่วนลดเป็น % > 100 หรือจำนวนเงินมากกว่ายอดที่ต้องชำระ → ต้อง clamp ไม่ให้ discountAmount เกิน amountDue (ปัจจุบัน clamp ด้วย `Math.min(amountDue, ...)`) — แต่ input เองไม่ได้ block ค่าติดลบ (`min={0}` เป็นแค่ UI hint ของ `<input type=number>`, ไม่ใช่ hard validation) → ทดสอบใส่ค่าติดลบว่ายังคำนวณผิดหรือไม่
- สลับ "ประเภทส่วนลด" (ยกเว้น↔ลดหย่อน) หลังเลือกประเภทย่อยแล้ว → ต้อง reset ประเภทย่อยเป็นตัวแรกของลิสต์ใหม่เสมอ (ห้ามค้างค่าเดิมของอีกฝั่ง)
- เหตุผลยกเลิก = "อื่นๆ" แต่ไม่กรอกรายละเอียด → ปุ่มยืนยันยกเลิก disabled; เหตุผลอื่นไม่บังคับกรอกรายละเอียด
- เปิด modal เดียวกันสองครั้งซ้อน (double-click แถว) — ต้อง idempotent ไม่เปิดซ้อนสอง modal
- ค้นหาด้วยคำที่ไม่ตรงใครเลย → ตารางว่าง แสดง `emptyMessage` "ไม่มีรายการในคิวการเงิน" ไม่ crash
- ออกเลขที่ใบเสร็จเมื่อทุกแถวเดิมถูกยกเลิกหมด (ไม่มี receiptNo ให้ parse) → `nextReceiptNo` fallback เป็น `999 + 1 = 1000` ไม่ throw
- แถวที่มี "ค่าใช้จ่ายอื่นๆ" เพิ่มมาแล้ว (category `other`, `addedManually: true`) ต้องถูกจัดกลุ่มเข้าหมวด "ค่าบริการอื่นๆ" ใน modal ถูกต้อง ไม่ตกหล่น

## 2. ค่าใช้จ่ายอื่นๆ — Other Charges (§2.3)

### Use cases

| # | Actor | Scenario | Expected result |
|---|---|---|---|
| UC-2.1 | แคชเชียร์ | กด "เพิ่มค่าใช้จ่าย" ที่แถวผู้ป่วยใดก็ได้ (ไม่จำกัดสถานะ) | เปิดฟอร์ม รายการ/จำนวนเงิน/สิทธิ/หน่วยงานที่ทำ/หน่วยงานที่ส่ง/แพทย์ |
| UC-2.2 | แคชเชียร์ | กรอกครบ + บันทึก | รายการใหม่ (category=`other`) ถูกเพิ่มเข้า items ของแถว, ยอดชำระ/ยอดค้างชำระอัปเดตตาม coverage ratio เดิมของ visit นั้น |
| UC-2.3 | แคชเชียร์ | เปิดใบเสร็จของแถวที่เพิ่มค่าใช้จ่ายอื่นๆ | เห็นรายการใหม่อยู่ในหมวด "ค่าบริการอื่นๆ" พร้อมยอดที่ปรับแล้ว |

### Edge cases

- จำนวนเงิน = 0 หรือค่าติดลบ → ปุ่มบันทึกต้อง disabled (`canConfirm = ... && Number(amount) > 0`)
- รายการ (label) ว่าง → disabled
- เพิ่มค่าใช้จ่ายให้แถวที่สถานะ "ชำระแล้ว" หรือ "ยกเลิกใบเสร็จ" — ปัจจุบันระบบ**ไม่ห้าม** (ปุ่มเปิดได้ทุกสถานะ) → ควรตัดสินใจว่า business rule จริงอนุญาตหรือไม่ (มักไม่ควรแก้ไขใบเสร็จที่ปิดยอดแล้ว) — ยังไม่มี guard
- เพิ่มหลายรายการติดกันในแถวเดียว (id `other-manual-${r.items.length}`) — ต้องไม่ชนกัน id ซ้ำเมื่อรายการก่อนหน้าถูกลบ (ปัจจุบันไม่มีปุ่มลบรายการที่เพิ่ม จึงยังไม่เกิด แต่ถ้าเพิ่ม delete ในอนาคตต้องคำนวณ id ใหม่)
- ตัวเลขทศนิยม (เช่น 99.5) → `Math.round` ที่ covered/patientPortion อาจทำให้ยอดรวมคลาดเคลื่อนสะสมทีละ ±1 บาท (rounding drift) เมื่อเพิ่มหลายรายการ
- coverage ratio ของ visit ที่ `totalCharge === 0` (ไม่ควรเกิดในข้อมูล mock ปัจจุบัน แต่ถ้าเกิด) → `ratio` ต้องไม่ NaN (มี guard `r.totalCharge > 0 ? ... : 0` แล้ว)

## 3. ปรับสถานะรับชำระ — Payment Status Correction (§2.4)

### Use cases

| # | Actor | Scenario | Expected result |
|---|---|---|---|
| UC-3.1 | แคชเชียร์ | ติ๊กเลือกหลายแถว, เลือกสถานะใหม่, กรอกผู้แก้ไข, กด "บันทึกการปรับสถานะ" | ทุกแถวที่เลือกเปลี่ยนสถานะพร้อมกัน, ปุ่มแสดงจำนวนรายการที่เลือกแบบ real-time |
| UC-3.2 | แคชเชียร์ | กด "เลือกทั้งหมด" | ทุกแถวถูกติ๊ก, ปุ่มนับ = queue.length |
| UC-3.3 | แคชเชียร์ | คลิกที่ตัวแถว (ไม่ใช่ checkbox) | ติ๊ก/ถอนติ๊กแถวนั้นได้เหมือนกัน (ทั้งแถวคลิกได้) |

### Edge cases

- คลิกตรง checkbox โดยตรง → ต้อง `stopPropagation` ไม่ให้ row's onRowClick ยิงซ้ำ (toggle สองครั้งจะหักล้างกันเอง) — มี guard แล้ว ต้อง regression-test เวลาแก้ Table component
- เลือก 0 แถวแล้วกดบันทึก → ปุ่มต้อง disabled (`selected.size > 0`)
- ไม่กรอกชื่อผู้แก้ไข → disabled
- เลือกสถานะเดิมที่แถวมีอยู่แล้ว (เช่นเลือกแถวที่ paid อยู่แล้ว แล้วตั้งเป็น paid อีก) — ระบบไม่ block, เขียนทับค่าเดิมเงียบๆ — อาจต้องการ warning ถ้า business rule ต้องการ audit ว่าไม่มีการเปลี่ยนแปลงจริง
- ปรับสถานะ "ชำระแล้ว" → "รอชำระเงิน" ของแถวที่เคยมี receiptNo/paymentMethod อยู่แล้ว — ปัจจุบัน**ไม่ล้าง**ค่าเดิม (receiptNo/amountReceived ยังค้างอยู่) ทำให้แถวที่ "รอชำระเงิน" มีเลขที่ใบเสร็จค้าง → ต้องตัดสินใจว่าควร clear หรือเก็บไว้เป็นประวัติ
- เลือกแถวข้ามหน้า/ข้าม filter (ถ้าในอนาคตมี pagination) — ปัจจุบันไม่มี pagination ในหน้านี้ ยังไม่ต้องกังวล

## 4. ลายเซ็นใบเสร็จ — Signature (§1.5.4)

### Use cases

| # | Actor | Scenario | Expected result |
|---|---|---|---|
| UC-4.1 | เจ้าหน้าที่ | กด "เพิ่มลายเซ็น" → โหมด "เลือกลายเซ็นที่บันทึกไว้" → ค้นหาชื่อ → เลือก | preview ลายเซ็น (SVG cursive-text) + auto-fill ชื่อผู้เซ็น |
| UC-4.2 | เจ้าหน้าที่ | สลับไปโหมด "สร้างลายเซ็น" → วาดด้วยเมาส์/นิ้ว | canvas capture stroke เป็น data URL |
| UC-4.3 | เจ้าหน้าที่ | สลับไปโหมด "อัปโหลดรูป" → เลือกไฟล์รูป | preview รูปที่อัปโหลด |
| UC-4.4 | เจ้าหน้าที่ | กรอกชื่อผู้เซ็น + กด "ยืนยันลายเซ็น" | สถานะแถวเป็น "เซ็นแล้ว", ปุ่มเปลี่ยนเป็น "ดูลายเซ็น" / "เซ็นใหม่" |
| UC-4.5 | เจ้าหน้าที่ | กด "ดูลายเซ็น" ของแถวที่เซ็นแล้ว | เปิด popup แสดงรูปลายเซ็น + ชื่อผู้เซ็น |
| UC-4.6 | เจ้าหน้าที่ | กด "เซ็นใหม่" ของแถวที่เซ็นแล้ว | เปิดฟอร์มเดิม โดย preload ลายเซ็น/ชื่อเดิมไว้ให้แก้ไข |

### Edge cases

- สลับโหมดไปมาโดยยังไม่ยืนยัน → ค่า `dataUrl` ต้อง reset ให้เหมาะสมต่อโหมด (โหมด draw ต้องเคลียร์ canvas เก่า) — ปัจจุบัน logic: `if (m.key !== 'saved') setDataUrl(m.key === 'draw' ? null : dataUrl)` → สลับจาก upload→draw จะเคลียร์ถูกต้อง, แต่สลับ draw→upload จะ**คงค่า dataUrl เดิมของ draw ไว้** (อาจไม่ตั้งใจ ควร reset เป็น null ด้วยเช่นกันเพื่อไม่ให้ upload mode โชว์ลายเซ็นที่วาดค้างอยู่โดยไม่มีไฟล์จริง)
- ยืนยันโดยไม่มี dataUrl (เช่นเลือกโหมด upload แต่ไม่แนบไฟล์) → ปุ่มต้อง disabled (`canConfirm = !!dataUrl && signerName...`)
- ยืนยันโดยไม่กรอกชื่อผู้เซ็น (แม้มี dataUrl แล้ว) → disabled
- ค้นหาชื่อในโหมด "เลือกลายเซ็นที่บันทึกไว้" ที่ไม่ตรงใครเลย → ลิสต์ว่าง ไม่มี state ว่าง (ควรเพิ่มข้อความ "ไม่พบชื่อ" ถ้าต้องการ UX ที่ดีกว่า — ปัจจุบันแค่ว่างเฉยๆ)
- อัปโหลดไฟล์ที่ไม่ใช่รูปภาพ (accept='image/*' เป็นแค่ hint, browser บางตัวยัง bypass ได้) → `<img src={dataUrl}>` จะ broken image, ไม่ crash แต่ UX ไม่ดี
- อัปโหลดไฟล์ขนาดใหญ่มาก (หลาย MB) → data URL ยาวมาก อาจทำให้ state/DOM หนักถ้ามีหลายแถวเซ็นพร้อมกัน (ยังไม่มีการจำกัดขนาดไฟล์)

## 5. ทะเบียนรายรับ — Revenue Register (§1.5.5)

### Use cases

| # | Actor | Scenario | Expected result |
|---|---|---|---|
| UC-5.1 | หัวหน้าการเงิน | เปิดแท็บ | เห็น chip สรุปยอดต่อวิธีชำระ 4 แบบ + ยอดรวม, ตารางเรียงตามเวลา (ไม่ใช่ string sort) |
| UC-5.2 | หัวหน้าการเงิน | กรองด้วยสิทธิ / ประเภทรายการ / วันที่ | ตาราง + chip สรุปยอด กรองตามเงื่อนไขพร้อมกัน (AND) |
| UC-5.3 | หัวหน้าการเงิน | กด "พิมพ์" | เรียก `window.print()` ของเบราว์เซอร์ |

### Edge cases

- ไม่มีรายการที่ตรงเงื่อนไข (เช่นกรองสิทธิที่ไม่มีใครจ่ายแล้ว) → ตารางว่าง, chip สรุปต้องแสดง ฿0 ไม่ใช่ NaN/undefined
- กรองประเภทรายการที่ไม่มีใน items ของ receipt ไหนเลย (เช่น "รังสีวินิจฉัย" ถ้าไม่มีใครสั่ง) → ผลลัพธ์ว่างถูกต้อง
- เวลา "8:00" vs "10:14" ต้องเรียงถูกจริง (bug เดิมที่แก้แล้ว) — ต้อง regression-test ทุกครั้งที่แก้ mock data time format
- ใบเสร็จที่ "ยกเลิกใบเสร็จ" ไปแล้ว **ต้องไม่ปรากฏ** ในทะเบียนรายรับ (filter เฉพาะ `status === 'paid'`) — ทดสอบว่า void แล้วหายจากลิสต์นี้จริง
- filter สิทธิ + ประเภทรายการพร้อมกันแบบไม่มีใครตรงทั้งคู่ → ต้องว่าง ไม่ error
- ตัวกรองวันที่ (FilterDateTag) **กรองจริงแล้ว** (`matchesDateFilter`) — แต่กรองที่ field ผิด และทำให้
  แท็บนี้ว่างเปล่าตั้งแต่เปิด ดู [DEF-1](#def-1--ทะเบียนรายรับ--ยอดค้างชำระ-ว่างเปล่าตั้งแต่เปิดแท็บ-)
  และ [DEF-2](#def-2--ทะเบียนรายรับ-ใช้-วันที่เข้ารับบริการ-แทน-วันที่รับชำระเงิน-)
- ชำระเงินสดวันนี้ให้ผู้ป่วยที่ visit เมื่อวาน → ใบเสร็จต้องขึ้นในทะเบียนรายรับ **ของวันนี้**
  (วันที่รับเงิน) ไม่ใช่ของเมื่อวาน — เป็นหัวใจของ §1.8.1.12/§1.8.5.3 และเป็นเคสที่ DEF-2 ทำพัง
- ชำระเงินข้ามเที่ยงคืน (visit 23:50, จ่าย 00:05) → ต้องนับเป็นรายรับของวันใหม่ และต้องไม่หลุด
  จากยอดตัดยอดประจำวันทั้งสองวัน
- ใบเสร็จที่ยอดสุทธิ ฿0 (สิทธิจ่ายเต็ม) → ต้องยังปรากฏในทะเบียนรายรับ (เป็นรายการที่เกิดขึ้นจริง)
  แต่ไม่เพิ่มยอดรวมเงิน — ตรวจว่า chip สรุปไม่นับซ้ำ/ไม่ตกหล่นจำนวนใบ

## 6. ยอดค้างชำระ — Outstanding Follow-up (§1.5.6)

### Use cases

| # | Actor | Scenario | Expected result |
|---|---|---|---|
| UC-6.1 | เจ้าหน้าที่ติดตามหนี้ | ค้นหาชื่อ/HN, กรองแผนก/สถานะการเบิกจ่าย | ตารางกรองตรง, ยอดรวมด้านบนอัปเดตตามผลกรอง |
| UC-6.2 | เจ้าหน้าที่ | กด "บันทึกติดตาม" → กรอกบันทึก+ชื่อ+เลือกสถานะ+แนบเอกสาร → บันทึก | ประวัติการติดตามสะสมเป็น log (ไม่ทับของเดิม), badge "สถานะติดตาม" นับจำนวนครั้ง, สถานะการเบิกจ่ายอัปเดตที่ตาราง |
| UC-6.3 | เจ้าหน้าที่ | เปิด popup ติดตามซ้ำที่แถวเดิม | เห็นประวัติการติดตามครั้งก่อนๆ ทั้งหมดเรียงลำดับ |
| UC-6.4 | เจ้าหน้าที่ | กด "ดูเอกสาร" ที่แนบไว้ | เปิดไฟล์ในแท็บใหม่ (blob URL) |

### Edge cases

- แนบเอกสารแล้วปิด popup โดยไม่กด "บันทึกการติดตาม" → ไฟล์ที่เลือกไว้ต้องหายไป ไม่ถูกบันทึกค้าง (เพราะ state อยู่ใน form ลูก ปิดแล้ว unmount ทิ้งเอง)
- URL ที่สร้างจาก `URL.createObjectURL(file)` ไม่เคย revoke → memory leak เล็กน้อยถ้าผู้ใช้แนบไฟล์ซ้ำๆ จำนวนมากในเซสชันเดียว (ไม่กระทบ functional test แต่ควรรู้ไว้)
- ไม่กรอกบันทึกหรือชื่อผู้บันทึก → ปุ่มบันทึกการติดตาม disabled
- แถวที่ "ชำระแล้ว" ระหว่างที่ยังมี popup ยอดค้างชำระเปิดค้างอยู่ (เช่นเปิดสองแท็บ/สอง action พร้อมกัน) — เนื่องจากเป็น session เดียว ไม่มี concurrency จริง แต่ต้องเช็คว่า `activeRow` อ้างอิงข้อมูลเก่า (stale) ถ้า queue เปลี่ยนระหว่างเปิด popup ค้างไว้
- สถานะการเบิกจ่ายเริ่มต้นเป็น `undefined` (แถวที่ยังไม่เคยติดตามเลย) → คอลัมน์ต้องแสดง "-" ไม่ crash, บันทึกครั้งแรกจะกำหนดค่าเริ่มต้นเป็น "ดำเนินการ" ให้อัตโนมัติ
- ค้นหาด้วยคำว่างแล้วพิมพ์เว้นวรรคอย่างเดียว (`"   "`) → ต้อง trim แล้วถือเป็นค้นหาว่าง (ไม่กรองอะไรออก) — ทดสอบว่า `.trim()` ทำงานถูกจุดนี้
- แท็บนี้ใช้ default `วัน: วันนี้` กรองที่ `visitDate` เหมือนทะเบียนรายรับ → **ว่างเปล่าตั้งแต่เปิด**
  ดู [DEF-1](#def-1--ทะเบียนรายรับ--ยอดค้างชำระ-ว่างเปล่าตั้งแต่เปิดแท็บ-). ที่ถูกต้องคือ "ยอดค้างชำระ"
  ไม่ควรผูกกับวันเดียว — หนี้ค้างข้ามวัน/ข้ามเดือนคือแก่นของหน้านี้ ค่าเริ่มต้นควรเป็น "ทั้งหมด"
  หรือช่วงย้อนหลัง ไม่ใช่ "วันนี้"
- ผู้ป่วยค้างชำระข้ามเดือน (visit เดือนที่แล้ว ยังไม่จ่าย) → ต้องยังติดตามได้ และยอดต้องรวมใน
  การ์ด "ยอดค้างชำระ" ด้านบนเสมอ ไม่ว่าตัวกรองวันจะเป็นอะไร (การ์ดสรุปคิดจาก `financeSummary(queue)`
  ทั้งชุด ส่วนตารางคิดจากผลกรอง — ทั้งสองค่านี้ **จะไม่ตรงกัน** โดยตั้งใจ ต้องอธิบายให้ผู้ใช้เข้าใจ
  หรือทำ label กำกับว่าตัวเลขไหนคือ "ตามตัวกรอง")
- แนบเอกสารเป็นไฟล์ประเภทที่เบราว์เซอร์เปิดเองไม่ได้ (.doc, .zip) → ลิงก์ "ดูเอกสาร" จะดาวน์โหลดแทน
  การเปิดดู — ยอมรับได้ แต่ต้องไม่ทำให้แท็บใหม่ค้างขาว
- ช่องแนบไฟล์เป็น `<input type="file">` ดิบ ไม่ผ่าน DS wrapper (ผิดกฎ CLAUDE.md "no browser-default
  input chrome") → หน้าตาไม่ตรงกับ input อื่นในระบบ ควร refactor

## 10. นำเข้าไฟล์ สปสช. (Import)

### Use cases

| # | Actor | Scenario | Expected result |
|---|---|---|---|
| UC-10.1 | เจ้าหน้าที่การเงิน | กด "เลือกไฟล์เพื่อนำเข้า" → เลือกไฟล์ .csv/.txt | ระบบอ่านไฟล์, นับจำนวนบรรทัด, เพิ่มเข้า "ประวัติการนำเข้า" พร้อมชื่อไฟล์+เวลา |
| UC-10.2 | เจ้าหน้าที่การเงิน | นำเข้าไฟล์หลายไฟล์ติดกัน | ประวัติสะสมเรียงใหม่สุดอยู่บนสุด |

### Edge cases

- ไฟล์ว่างเปล่า (0 byte) → `rowCount` ต้องเป็น 0 ไม่ error
- ไฟล์ที่มีแต่บรรทัดว่าง/เว้นวรรค → ต้องนับหลัง `.filter((l) => l.trim())` ไม่นับบรรทัดเปล่า
- ไฟล์ที่ไม่ใช่ text จริง (เช่น .xlsx เปลี่ยนนามสกุลเป็น .csv) → `FileReader.readAsText` จะได้ binary garbage, `rowCount` จะเพี้ยนแต่ไม่ crash — ควรพิจารณา validate MIME/นามสกุลถ้าต้องการความถูกต้องจริง
- กดปุ่มเลือกไฟล์แล้วกด "ยกเลิก" ใน native file picker (ไม่เลือกไฟล์) → ต้องไม่มีอะไรเกิดขึ้น (guard `if (!file) return`)
- ไฟล์ขนาดใหญ่มาก (หลายสิบ MB) → `readAsText` เป็น synchronous-feeling บน main thread สำหรับไฟล์ใหญ่ อาจหน่วง UI ชั่วครู่ (ไม่มี progress indicator)
- "การนำเข้า" นี้เป็นแค่ log เฉยๆ — **ไม่เชื่อมกับข้อมูลการเงินจริงในระบบ** (documented) ดังนั้นห้าม test ว่าตัวเลขอื่นในระบบเปลี่ยนตามไฟล์ที่นำเข้า
- ตั้งแต่มีแท็บ "รายงานการเงิน" (§13) ข้อจำกัดนี้กลายเป็น **ช่องว่าง TOR ที่วัดผลได้แล้ว**:
  §1.8.6.7 ระบุว่าไฟล์ สปสช. ต้อง "ใช้เป็นข้อมูลประกอบการทำรายงานทางการเงิน" — เมื่อมีรายงานจริง
  แล้วแต่ยอดที่นำเข้าไม่ไหลไปที่ไหนเลย ข้อนี้ควรเป็น **partial ไม่ใช่ done**
- เมื่อทำ parser จริง ต้องรองรับ: ไฟล์ 18 แฟ้ม/12 แฟ้ม, encoding TIS-620 (ไม่ใช่ UTF-8),
  บรรทัด header/trailer ที่ไม่ใช่ข้อมูล, เลขที่อ้างอิงซ้ำกับที่เคยนำเข้าแล้ว (ต้อง dedupe ไม่ใช่
  บวกยอดซ้ำ), และงวดการจ่ายที่ครอบคลุมหลายเดือนพร้อมกัน
- นำเข้าไฟล์ของงวดเดียวกันซ้ำสองครั้ง → ต้องเตือน/แทนที่ ไม่ใช่บวกยอดทบเข้าไปอีกรอบ

- สิทธิที่ไม่มีใครอยู่เลย (เช่นถ้าทุกคนไม่ใช่ "ชำระเงินเอง") → แถวนั้นต้องแสดง 0/฿0 ไม่ใช่หายไปจากตาราง — **[แก้แล้ว]** เดิม `byRights` สร้าง group เฉพาะตอนเจอแถวที่มีสิทธินั้นจริง (`if (!groups[key]) groups[key] = ...` อยู่ใน loop) ทำให้กลุ่มที่ไม่มีใครใช้หายไปเงียบๆ — แก้โดย initialize ทั้ง 4 กลุ่มจาก `RIGHTS_GROUPS` ก่อนเสมอ แล้วค่อย accumulate ทับ (`src/pages/finance/sections/CashierAuditSection.jsx`)
- ค้นหาด้วย HN บางส่วน (เช่น "005") vs ชื่อบางส่วน (เช่น "สุดา") → ต้อง match ได้ทั้งคู่ (`includes`)
- ผู้ป่วยที่มีมากกว่า 1 visit ใน queue (ไม่มีในข้อมูล mock ปัจจุบันเพราะ 1 คน = 1 แถว) → `find` จะได้แค่แถวแรกที่ตรง ไม่ใช่ "ล่าสุดจริง" ถ้าในอนาคตมีหลาย visit ต่อ HN

  (เพราะ chart primitive พิมพ์ค่าดิบเป็น data label ตัวเลข 8 หลักไม่พอที่) → ทุกกราฟต้องมี caption "หน่วย:"
  กำกับเสมอ ถ้าแก้กราฟแล้วลืม caption ถือว่า regression
- ปีงบที่กำลังเดินอยู่มีข้อมูลไม่ครบ 12 เดือน → ต้อง**ตัดเดือนที่ยังไม่ถึงทิ้ง** ไม่ใช่ plot เป็น 0
  (0 จะทำให้กราฟดิ่งลงเหมือนรายรับหาย) — ปัจจุบันตัดด้วย `year.elapsed`
- ค่าเฉลี่ยต่อเดือนต้องหารด้วย **จำนวนเดือนที่ผ่านมาจริง** ไม่ใช่ 12 เสมอ
- `คงเหลือสุทธิ` ติดลบ (รายจ่าย > รายรับ) → ต้องแสดง `-฿X` (เครื่องหมายหน้าสัญลักษณ์เงิน) ไม่ใช่ `฿-X`
- ยอดวันนี้จาก queue ถูกกระจายเข้าหมวดรายรับตามสัดส่วนราคาเต็มของแต่ละ visit → ผลรวมของทุกหมวด
  ต้องเท่ากับ `รายรับรวม` เป๊ะ ห้ามเกินจากการปัดเศษ (ทดสอบด้วยการจ่ายเงินหลายใบติดกันแล้วบวกมือ)
- ใบเสร็จที่ถูก void หลังจ่ายไปแล้ว → ต้องหายจากยอด "วันนี้" ในรายงานทันที (นับเฉพาะ `status==='paid'`)
- ผู้ป่วยที่จ่ายด้วย **QR หรือโอนเงิน** → ต้องตกลงช่อง **e-Payment** ไม่ใช่ "เงินสด"; บัตรเครดิต/เดบิต →
  **เครดิต**; ช่อง **เงินบริจาค** ไม่มีทางมาจากคิว (ไม่มี payment method นี้) จึงมาจาก mock ล้วน
- กรองศูนย์เดียว + ปีงบปัจจุบัน → ยอดวันนี้ต้องนับเฉพาะใบเสร็จของศูนย์นั้น (map จาก `row.center`);
  ถ้าเพิ่มศูนย์ใหม่ใน mock queue แต่ลืมเพิ่มใน `CENTER_OF` ยอดของศูนย์นั้นจะ**หายเงียบ** — regression risk
- ตารางงบ: `ใช้ไป` ทุกหมวดรวมกันต้องเท่ากับ `รายจ่ายรวม` ของ §1.20.3.2 เสมอ (share รวมกัน = 1.0)
  ถ้าแก้ `BUDGET_CATEGORIES` แล้ว share ไม่ครบ 1 ตัวเลขสองหัวข้อจะขัดกันทันที
- % ใช้ไป > 100 → progress bar ต้อง clamp ที่ 100% แต่ตัวเลข % ต้องแสดงค่าจริง (เช่น 115.3%)
- ปีงบที่ไม่มีใน `BUDGET_ALLOCATION` (ถ้าเพิ่มปีใน `FISCAL_YEARS` แต่ลืมเพิ่ม allocation) → จะ throw
  ตอน `allocation[b.key]` — ควรมี guard ก่อนขึ้น production data
- กราฟทั้งหมดใช้ IntersectionObserver animate ตอนเลื่อนเข้า viewport → เทสต์อัตโนมัติที่ไม่ scroll
  จะจับได้แค่ค่า 0 ต้อง scroll เข้ามาก่อนวัดผล

### DEF-1 · ทะเบียนรายรับ + ยอดค้างชำระ ว่างเปล่าตั้งแต่เปิดแท็บ ✅

**ทำซ้ำ:** เปิด `/finance` → แท็บ "ทะเบียนรายรับ" (หรือ "ยอดค้างชำระ") โดยไม่แตะตัวกรองใดๆ
**ที่ควรเป็น:** เห็นใบเสร็จที่ชำระแล้ว 3 ใบ / ยอดค้างชำระ 4 ราย ตามการ์ดสรุปด้านบน
**ที่เป็นจริง:** "ไม่พบรายรับที่ตรงกับเงื่อนไข" · chip ทุกวิธีชำระ ฿0 · "ยอดค้างชำระรวม (0 ราย) ฿0"
ทั้งที่การ์ดบนหัวจอบอก `ชำระแล้ววันนี้ 3 · ฿617` และ `ยอดค้างชำระ ฿334` — ขัดกันเองในจอเดียว
**สาเหตุ:** ตัวกรองตั้งต้น `{ quick: 'today' }` ไปเทียบกับ `row.visitDate` ที่ mock ตรึงไว้
`'29 กรกฎาคม 2569'` ขณะที่ "วันนี้" คือ 31 ก.ค. 2569
**กระทบ TOR:** §1.8.5.1, §1.8.5.3, §1.8.6.1, §1.8.6.6 (ทุกข้อระบุ "แสดงผลค่าเริ่มต้นเป็นปัจจุบัน")
**แก้โดย:** `financePaymentPrototype.js` เลิก hardcode วันที่ — seed วันจากนาฬิกา (`thaiDate` +
`VISIT_DAYS_AGO`) โดยให้ visit ส่วนใหญ่เป็นวันนี้ และตั้งใจให้ 2 แถวค้างชำระเก่ากว่า (3 และ 12 วัน)
เพื่อให้เคสหนี้ข้ามวันมีของจริงให้เทสต์; `OutstandingSection` เปลี่ยน default เป็น `30days`
**ยืนยัน:** ทะเบียนรายรับขึ้น 3 ใบ `฿617` และยอดค้างชำระขึ้น `4 ราย ฿334` ตรงกับการ์ดด้านบนเป๊ะ

### DEF-2 · ทะเบียนรายรับ ใช้ "วันที่เข้ารับบริการ" แทน "วันที่รับชำระเงิน" ✅

**ทำซ้ำ:** ชำระเงินให้คิวใดก็ได้ตอนนี้ → ไปแท็บ "ทะเบียนรายรับ" → ดูคอลัมน์ "วันที่และเวลา"
**ที่ควรเป็น:** วันเวลาที่รับเงิน (`row.paidAt` — มีอยู่ในข้อมูลแล้ว)
**ที่เป็นจริง:** แสดง `row.visitDate`/`row.visitTime` และตัวกรองวันก็ยิงที่ field เดียวกัน
→ ใบเสร็จที่จ่ายบ่าย 2 ของ visit 8 โมงเช้า จะขึ้นเป็น 8 โมง และไปโผล่ในทะเบียนของ "วัน visit"
**กระทบ TOR:** §1.8.1.12 ("ค้นหา…วันที่รับชำระเงิน"), §1.8.5.3
**แก้โดย:** เพิ่ม `paidDate`/`paidTime` แยกจาก `visitDate`/`visitTime` ทั้งใน seed และใน `handlePay`;
ทะเบียนรายรับกรอง/เรียง/แสดงจาก `paidDate` และกำกับ `· visit <วันที่>` เมื่อคนละวันกัน
**ยืนยัน:** ชำระเงินให้ F007 (visit 10:42) เวลา 13:44 → ทะเบียนรายรับขึ้น `31 กรกฎาคม 2569 · 13:44 น.`

### DEF-3 · ติ๊กเลือกรายการไม่มีผลกับยอดเงิน ✅

**ทำซ้ำ:** คิว F007 → "ชำระเงิน" → เอาติ๊ก `Knee X-ray (2 views) ฿420` ออก
**ที่ควรเป็น:** ยอดรวม/สิทธิจ่าย/ยอดที่ต้องชำระ ลดลงตามรายการที่เหลือ
**ที่เป็นจริง:** `ยอดรวม ฿955` · `สิทธิ ฿764` · `ยอดที่ต้องชำระ ฿191` **ไม่ขยับเลย**
**สาเหตุ:** `FinancePaymentPage.jsx:357` เรียก `computeTotals(row.items, false)` — ส่ง
`selectedOnly = false` และใช้ `row.items` ทั้งชุด ส่วน state `selected` ถูกใช้แค่ enable/disable ปุ่ม
**กระทบ TOR:** §1.8.1.15 ("เลือกชำระเงินรายการร่วมจ่ายได้ ในกรณีใช้บริการเกินจากสิทธิ"), §1.8.1.3
**แก้โดย:** คิดยอดจาก `selectedItems` แล้วส่ง `paidItemIds` + `netDue` เข้า `handlePay`;
ใบเสร็จ (`ReceiptDetail`), คอลัมน์ "รายการ" ในทะเบียนรายรับ และการแยกหมวดรายรับในรายงาน
อ่านเฉพาะรายการที่ชำระจริง
**ยืนยัน:** F007 ทั้ง 4 รายการ = `฿955 / -฿764 / ฿191` → ติ๊ก X-ray ฿420 ออก = `฿535 / -฿428 / ฿107`
→ ติ๊กไม้ค้ำยัน ฿150 ออกอีก = `฿385 / -฿308 / ฿77` → ติ๊กกลับครบ = `฿955 / -฿764 / ฿191`
**ขอบเขตที่ยังไม่ทำ:** รายการที่ไม่ได้ติ๊กจะไม่ถูกยกไปเป็นยอดค้างของ visit นั้น (แถวยังกลายเป็น
`paid` ทั้งแถว) — partial payment จริงต้องมี settlement state รายบรรทัดซึ่ง mock นี้ไม่มี

## Cross-cutting edge cases (ทุกส่วนร่วมกัน)

1. **Reload หน้าเว็บ** — ทุก state (`queue`, `cutoff`, signatures, follow-ups, ฯลฯ) เป็น React state ล้วนๆ ไม่มี persistence layer → รีเฟรชแล้วข้อมูลทั้งหมดรีเซ็ตกลับเป็น seed เริ่มต้นจาก `FINANCE_QUEUE`
2. **หลายแท็บเบราว์เซอร์เปิดพร้อมกัน** — ไม่มีการ sync ข้าม tab (ไม่ใช่ shared state/localStorage) → แก้ไขในแท็บหนึ่งจะไม่ปรากฏในอีกแท็บจนกว่าจะ reload
3. **ลำดับการทำงานข้ามส่วน (cross-section race)** — เช่น เปิด modal ชำระเงินของ F005 ค้างไว้ (ยังไม่กด save) แล้วไปหน้า "ปรับสถานะรับชำระ" เปลี่ยนสถานะ F005 เป็น "ยกเลิกใบเสร็จ" จากอีกที่ แล้วกลับมากด save ที่ modal เดิม → modal เดิมจะเขียนทับสถานะเป็น "ชำระแล้ว" อีกที (stale closure ทับข้อมูลใหม่กว่า) — ยังไม่มี optimistic-lock/version check
4. **ภาษา/ตัวเลขไทย** — วันที่ทั้งหมดใช้ `toLocaleDateString('th-TH')` (ปี พ.ศ.) ต้อง sanity-check ว่าเบราว์เซอร์ที่ใช้ทดสอบ render ปี พ.ศ. ถูกต้อง ไม่ใช่ปี ค.ศ. หลุดมา
5. **จำนวนเงินทศนิยม** — ทุกจุดใช้ `Math.round` ตัดเป็นจำนวนเต็มบาท ไม่รองรับสตางค์ — ถ้า business ต้องการทศนิยม ต้อง refactor `formatBaht`/การคำนวณทั้งหมด
6. **"วันนี้" ถูกตรึงไว้ในข้อมูล mock** — `visitDate: '29 กรกฎาคม 2569'` เป็นค่าคงที่ ขณะที่ตัวกรอง
   และ `todayThai()` อ่านนาฬิกาเครื่องจริง → **ยิ่งเวลาผ่านไป ระบบยิ่งเพี้ยน** และเป็นต้นตอของ DEF-1
   ทุกครั้งที่เดโมให้ลูกค้าดู ต้องเช็คก่อนว่า mock date ยังสมเหตุสมผลกับวันจริงหรือยัง
   (ทางแก้ระยะยาว: derive วันที่ mock จาก `new Date()` ตอน seed ไม่ใช่ hardcode)
7. **การ์ดสรุปบนหัวจอ vs ตารางในแท็บ** — การ์ด 4 ใบคิดจาก `financeSummary(queue)` ทั้งชุดเสมอ
   ส่วนตารางแต่ละแท็บคิดจากผลกรองของแท็บนั้น → สองตัวเลขนี้ไม่ตรงกันได้โดยชอบธรรม
   ต้องตัดสินใจว่าจะ label ให้ชัด หรือให้การ์ดตอบสนองตัวกรองด้วย
8. **ตัวเลขเดียวกันถูกคำนวณคนละที่** — ยอดวันนี้ปรากฏใน 3 ที่ (การ์ดสรุป, chip ในทะเบียนรายรับ,
   tile ในรายงานการเงิน) โดยคำนวณแยกกัน → ต้องมี regression test ที่ยืนยันว่าทั้งสามตรงกัน
   ทุกครั้งที่แตะ logic การชำระเงิน (ตอนนี้ **ไม่ตรง** เพราะ DEF-1)
9. **สิทธิ์ผู้ใช้ (role)** — ทุกแท็บเปิดได้หมดโดยไม่มีการเช็ค role เลย ทั้งที่ "ตั้งค่าราคาขาย",
   "ปรับสถานะรับชำระ", "ตัดยอด/นำส่งเงิน" และ "ปรับสิทธิ" ควรจำกัดเฉพาะหัวหน้า/ผู้ดูแลระบบ
   — เมื่อเชื่อม auth จริงต้องเพิ่ม use case ชุด "ผู้ใช้ที่ไม่มีสิทธิ์เข้าถึงแท็บนี้"
10. **Audit trail** — void/ปรับสถานะ/ปรับสิทธิ บันทึกผู้ทำไว้บนแถว แต่ไม่มี log กลางที่เรียงตามเวลา
    และไม่ส่งไป `/audit` → ถ้าลูกค้าขอ "ใครทำอะไรเมื่อไหร่" ตอนตรวจรับ ตอบไม่ได้จากหน้านี้
